# Spec: SPEC 独立审查与复审反馈

## Delivery Contract

### Source

本任务 source.md 保存 2026-11-17 用户原话与对话确认后的实施范围，以及 11 月 18–19 日继续真实模型试验的授权；来源是当前用户会话，范围整理与逐字原文明确区分。

### Outcome

- O-1: SPEC 阶段可以对照可读取原文启动独立审查，取得具体缺口、反例或澄清问题。
- O-2: 作者修订或提供反证后，可以逐项复审并保留原发现身份，确认修订或撤回错误发现。
- O-3: 调用失败、输入变化与无依据输出不会伪装成审查完成；前置反馈不改变现有推进或最终验证。

### Boundary

承诺：审查入口、原文快照、有限结构协议、独立派发、修订复审记录、建议性流程指导与程序/运行时验证。排除：强制准入、自动需求决策、来源认证平台、外部系统自动采集、状态机扩展、模型质量保证和未经批准的付费评测。

### Oracle

真实 Cordis / ToolRuntime / LocalFileSystem 调用工具，使用受控模型结果验证原文传递、各类复审动作、失败留痕和状态不变；全量 build/test/smoke 与 tarball 隔离 profile 检查。真实语义发现能力另外评测，不用桩证明。

### AC mapping

- O-1 → AC-001, AC-002
- O-2 → AC-003
- O-3 → AC-004, AC-005, AC-006
- 验证与交接 → AC-007

## Acceptance Criteria

- AC-001: SPEC 中注册的 Intent / Spec 与工作区内原始需求快照可以传给独立审查者；不要求 plan 或功能已实现，原文与澄清/作者推断可区分。
- AC-002: 审查反馈包含出处、Spec 位置、问题、具体反例与建议；引用必须能在所指快照中找到，不返回最终 approve/reject，不以结构检查宣称语义完备。
- AC-003: 复审显式关联同任务已完成前轮，作者与审查者均须逐项覆盖未解决发现；支持 addressed、withdrawn、open、needs_clarification 并保留未解决发现的编号。
- AC-004: 来源缺失、模型异常、无效结构、复审漏项、取消和输入变化不会产生完成反馈；每次最多一次模型派发，记录执行与失败，不解析自由文本猜结果。
- AC-005: SPEC 审查不修改 state.yaml、AC 登记、已有问题状态或 verification.json，不新增推进门禁；失败审查不妨碍按既有规则进入 PLANNED。
- AC-006: 共用的独立派发保持现有 sdlc_verify 语义、工具限制、取消和资源归还；保持原有包/组件分发结构。
- AC-007: 使用文档、流程指导、单测、真实运行时冒烟和隔离 tarball 检查覆盖入口及复审；全量 verify 通过。如实区分程序验证与真实模型评测的已覆盖/未覆盖范围，保留实际配置、逐轮结果、失败和用量，不把小样本宣称为模型质量保证。

## Requirements

审查围绕原始承诺与可证伪验收，必要依赖可根据目标推导，不能借最佳实践扩需求。作者反证不是结论；复审可以撤回错误发现。来源的 origin / kind 为调用方声明，哈希不认证来源。

## Design

在 verify 组件新增 sdlc_spec_review；提取共用 runtime。纯函数定义反馈协议与提示词，工具层读取有界快照并落盘 spec-reviews 记录，使用显式前轮关联。最终验证的 Schema / 状态与事件统计保持独立。

## Areas of concern

模型误报、反复争议、作者提供不完整原文、提示词遵循、受限工具的职责边界。通过记录与后续行为评测暴露限制，首版不以新门禁掩盖这些不确定性。
