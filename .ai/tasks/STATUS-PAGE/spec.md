# Spec: sdlc_status 的可达性

## Requirements

### R1 向后兼容（逐字）

不传任何新参数时，工具的返回**与改动前完全一致**：同样的 `tasks` 数组、
同样的 summary、同样的截断提示。已有的调用方不应察觉任何差别。

⚠️ **"输出"包含渲染文本，不只是 JSON 字段。** 我在实现时一度违反这条：
默认路径也产出并渲染了 `note`，于是**空仓库**（本仓库与测试场开局的状态）
从 `"没有任务。\n"` 变成 `"没有任务。\n没有更多了：offset=0 已越过总数 0\n"`
——没有任务却报"已越过总数"。独立验证者用 HEAD 的旧代码逐字对比抓到了它。

所以：**`note` 只在调用方显式传了 `task_id` / `offset` / `limit` 时产出**。

### R2 分页

新增两个可选参数：

| 参数 | 类型 | 默认 | 上限 |
|---|---|---|---|
| `offset` | integer ≥ 0 | 0 | — |
| `limit` | integer ≥ 1 | 50 | **200** |

- `offset` 是"跳过前 N 个"，`limit` 是"最多显示 M 个"
**切窗分两种模式，取决于调用方有没有显式要求分页：**

| 调用 | 切窗序 | 回答什么 |
|---|---|---|
| 不传参数 | **`scanTasks` 的呈现序**（= 改动前的行为） | "最该看的是什么" |
| 传了 `offset`/`limit` | **task id 的码元序**（与时间无关） | "把所有都看一遍" |

- **不传参数时**保持呈现序，是为了 R1 的逐字兼容，也为了看板的本职：
  它的理由是"一眼看到要动手的"。60 任务混合夹具下，旧首行是
  `✗ ZZ-001 — 读不出来`，而按 id 序会变成 `· AA-001 [SPEC]`——**一个坏任务都不在里面**。
- **显式分页时**用 id 码元序，才可能"同一 offset 给到同一批"：
  呈现序的首键是停滞分组（error > stale > waiting > 其余），
  而"是否 stale"由 now 与 updated 之差决定。

⚠️ **这条我错过两次，都记在案：**

**错 1（原本的缺陷）**：直接按传入顺序 `slice()` 切窗。独立验证者用 3 个任务、
0.5 秒间隔实测：第 1 页取到 `[A-1, B-1]`，同一个 `offset=2` 在 0.5 秒后返回
`[B-1]`——**B-1 重复，C-1 永远取不到**（仓库内容一字未改，只是任务跨过了停滞阈值）。
我原来的论证是错的：我只查了比较器末尾有 `localeCompare` 兜底，**漏掉了首键会随时间变**。

**错 2（我修错 1 时引入的）**：把**整页**改成按 id 字典序选人，于是默认调用
不再显示最该看的 50 个。验证者用混合夹具实测出上面那个首行差异。
而我的冒烟夹具是同质的（id 序恰好等于紧迫序），**天然看不见**。

**切窗键必须是码元比较，不能用 `localeCompare`**：后者不是全序——两个不同 id
在 ICU 下可能比较为 0（零宽空格 U+200B、软连字符 U+00AD 等会被忽略），
那时稳定排序退回传入顺序，错 1 原样回来。验证者用 `K-1` 与 `K-\u200B1`
在纯函数层与真实工具端到端都复现了。
- 翻页覆盖全部任务时**不重不漏**：各页任务 id 的并集 == 全部任务，
  且两两交集为空

### R3 offset 超出总数

`offset >= 总数` 时：

- `tasks` 为空数组（这是事实）
- **但必须明确告知**"没有更多了"，不能让调用方以为出错或以为还有
- 明确告知的方式：`note` 字段 + 渲染文本里一句话

### R4 单任务详情

新增可选参数 `task_id`：

- 只返回那一个任务（`tasks` 长度为 1），**不受 offset / limit 影响**
- `task_id` 与 `offset`/`limit` 同时给出时：**`task_id` 优先，其余被忽略**，
  并在 `note` 里说明忽略了什么（不静默丢弃参数）
- `task_id` 不存在时：**抛错**（`isError`），而不是静默返回空数组。
  理由：调用方明确要一个任务，给空列表无法区分"不存在"与"扫描坏了"

### R5 limit 被夹到上限时要说出来

`limit > 200` 时夹到 200，并在 `note` 里说明"请求 N，实际 200"。
不静默夹——调用方可能据此判断"还想看更多"。

### R6 分页实现必须是**可独立单测的纯函数**

选择逻辑（按 id / offset / limit 取窗口，以及生成 note）抽成纯函数，
不穿过工具调度去测。

**理由（本项目的既定教训）**：`enforceCriteriaPolicy` 的"findings 被静默丢掉"
就是因为一直穿过整个工具调度被测，藏到最后一轮才暴露；移到纯函数层一次暴露。

### R7 仍然只读

新增参数不得引入任何写操作。本包冒烟的只读性断言
（调用前后整个文件树与 mtime 完全一致）必须继续通过。

## Design

### 新增的纯函数（`scan.ts`）

```ts
export interface Selection {
  /** 被选中的任务（保持传入顺序）。 */
  entries: TaskEntry[];
  /** 给调用方看的一句话：说明这次选择做了什么、以及是否是全部。 */
  note?: string;
  /** 是否是全部任务（没有因分页而遗漏）。 */
  complete: boolean;
}

export function selectTasks(
  entries: readonly TaskEntry[],
  opts: { taskId?: string; offset?: number; limit?: number },
): Selection
```

**注意 R4 的错误语义**：`task_id` 不存在时抛错。抛错还是返回空？
抛错——因为"明确要一个东西却没有"和"列表为空"是两件事，
前者是调用方需要知道的事实。

### 输出 schema 的增量

保持现有字段不动，**只新增**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `note` | string（可选） | 本次选择做了什么 / 是否被夹 / 是否还有更多 |
| `window_start` | number | 显示的是第几个（从 1 计）；单任务详情时为该任务的位置 |
| `window_end` | number | 显示到的位置（含） |
| `complete` | boolean | 是否显示了全部任务 |

⚠️ **`tasks` 的语义要写清楚**：它现在是"**本次显示**的任务"，
而不是"全部任务"（`total` 才是总数）。
改动前没有这个歧义，所以工具描述里必须补一句说明。

### 渲染

现有渲染是三段拼接：一句 summary、一个空行、若干任务行。

改为四段：

1. summary（不变）
2. **一行窗口说明**——仅在"不是全部"时出现（向后兼容 R1 要求默认路径不出现新行）
3. 空行
4. 任务行

窗口说明的文本形如：「显示第 51-72 个，共 120 个（还有 48 个，用 offset 继续）」。
**具体措辞留待实现时定**，但必须包含：本次范围、总数、以及怎么拿到剩下的。

### 参数解析的边界

- `offset` 给小数 / 负数 / 非数字：**抛错**（`isError`），不静默当作 0。
  参数错了要说出来——静默纠正会让调用方以为自己的参数生效了
- `limit` 同理

## Areas of concern

- **`tasks` 的语义发生了微妙的改变**（从"全部"到"本次显示"）。
  在不超过 50 个任务的仓库里，两者**看起来完全一样**——
  这正是最容易埋雷的地方。所以：
  ① 工具描述必须明确写 "the tasks SHOWN (see `total` for the count)"
  ② `complete` 字段让调用方能程序化地判断，而不是靠解析 summary 文字
  ③ 冒烟必须有一条**超过一页**的用例（否则这个区别永远测不到）

- **`note` 与现有的截断提示会重复**。现有实现已经在 `tasks` 末尾追加
  「… 还有 N 个未显示」。加了 `note` 之后，同一件事有两个地方说。
  必须定死：**`note` 是权威，末尾那行只在"未指定 offset/limit 且被默认截断"时保留**
  （为了向后兼容 R1）。也就是说默认路径保留旧文本，分页路径只用 `note`。

- **翻页的稳定性依赖于 `scanTasks` 的排序**。今天有 `localeCompare` 兜底，
  但这是个**隐式依赖**——如果将来有人动了比较器，翻页会悄悄重/漏。
  所以要有一条测试**直接钉住"同一输入两次调用顺序相同"**，
  而不是只在心里假设。

- **`task_id` 的存在性检查走的是"已扫描到的任务"**。如果调用方给了一个
  真实存在但扫描不到的任务（例如目录名与 task_id 不匹配、或 tasks_dir 配错），
  报的会是"找不到"而不是"目录配错了"。前者可能误导。
  缓解：错误信息里带上扫描根路径，让调用方能自己发现配错了。

## 规格过程中的查证

写意图时我留了一条 open question：「翻页时的排序是否稳定？」
**我没有先查就把它写成了疑问。** 查证结果：

`scanTasks` 的比较器链是 group → （同为 stale 时按 ageMs 倒序） → 状态 rank →
**`a.task.localeCompare(b.task)` 兜底**。所以顺序是**确定的**，翻页不会重/漏。

这个查证改变了规格的写法：如果排序不稳定，R2 就得先要求"引入稳定的全序"，
那是一个更大的改动。现在 R2 只需**依赖**已有性质，并加一条测试钉住它
（见 Areas of concern 的第三条）。

如实记在这里，而不是偷偷把意图里的问题删掉。

### R8 `truncated` 的语义（独立验证者提出）

`truncated` 表示"**有任务没显示**"，而不是"默认分页被截断了"。
旧式子 `!explicit && !sel.complete` 在显式分页时恒为 `false`，
调用方会以为看全了（`offset=0, limit=10, total=250` 时 `truncated=false`
而实际只显示了 10 个）——正确的判据是 `complete`。

新式子 `!sel.complete` 在默认路径下与旧实现**逐字等价**
（默认 limit=50：total ≤ 50 → false；total > 50 → true）。

⚠️ 但**渲染时不能跟着改**：那条旧的截断提示**行**属于 R1 的向后兼容，
必须继续只在"没传新参数"时追加。我第一版把两者混在一起，于是显式分页
也多了一行"… 还有 N 个未显示"，**把一个真实任务挤出了窗口**
（250 个任务下显示 201 条）——冒烟立刻抓到。

### R9 `window_start` / `window_end` 的口径必须与 `offset` 同一根轴

两者都是 **task id 码元序**上的位置（从 1 计），而不是呈现序。

⚠️ 我第一版用呈现序的位置，于是 `task_id=AA-001` 报成"第 4 个"
（3 个坏任务排在呈现序最前），而 `offset=0, limit=1` 返回的第一条正是它——
调用方按 `window_start` 去换算 `offset` 会取错页。独立验证者指出后已统一到 id 轴。
