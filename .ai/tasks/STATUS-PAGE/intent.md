# Intent: 让被截断的任务可达

## Problem

`sdlc_status` 一次最多显示 **50** 个任务。超过之后它会诚实地报出
「… 还有 N 个未显示（共 M 个）」，但**那些任务没有任何办法看到**：

- 没有分页参数（offset / limit）
- 没有按 id 查看单个任务的途径
- 没有过滤

后果是看板的核心承诺破了。它的描述写着「用**一次调用**回答『哪些任务卡住了』
『谁的裁决还没处理』」——而在任务超过 50 个之后，这个回答**是不完整的**，
且调用方无法补救（只能改配置或改代码）。

诚实的截断提示（"还有 N 个未显示"）比静默截断好得多，但它只解决了
**知情**问题，没解决**可达**问题。知道有 30 个任务看不见，和能看见它们，
是两件事。

## Proposed outcome

` sdlc_status` 支持两种新的查看方式，且**不改变默认行为**：

- **分页**：给定 `offset`，从第 offset 个开始显示；`limit` 可选（默认仍 50，硬上限）。
  可以连续翻页直到看完所有任务。
- **单任务详情**：给定 `task_id`，只显示那一个任务（不受分页影响）。

关键的可观察结果：

1. 不传任何新参数时，输出与现在**完全一致**（向后兼容）
2. 传 `offset` 时能取到原先够不着的那部分任务，且**每个任务恰好出现一次**
   （翻页不重不漏）
3. `offset` 超出总数时，明确说"没有更多了"，而不是给一个空列表让人以为出错
4. `task_id` 不存在时，明确说找不到，而不是静默返回空

## Affected users and systems

- 使用 `sdlc_status` 的 agent 与会话（唯一调用方）
- `packages/sdlc-status`：工具参数、输出 schema、`formatEntry` 的使用
- 输出 schema 新增字段 → 必须与 schema 定义逐项对齐（本项目有递归校验器会抓漂移）
- **不影响** `sdlc-task` / `sdlc-artifact` / `sdlc-verify`

## Constraints

- **只读**：绝不能因为分页而开始写文件。本包的冒烟有只读性断言
  （比对调用前后的整个文件树与 mtime），这条必须继续成立
- **向后兼容**：不传新参数时输出逐字不变——它是被别处依赖的稳定接口
- 不引入新的依赖
- 上限仍然必须存在（不能因为加了 offset 就允许一次拉 10000 条进上下文）

## Open questions

- **`task_id` 与 `offset` 同时给时怎么办？** 我倾向：`task_id` 优先且忽略 offset
  （单任务详情不受分页影响），但这是**需要明确写进规格**的语义，不能靠实现顺手决定。
- **`limit` 要不要暴露？** 暴露的话调用方能一次拉 200 条，上下文有风险；
  不暴露的话只能固定页大小翻页。我倾向暴露但设硬上限，并在超出时**明确告知被夹到多少**。
- **翻页时的排序是否稳定？** 现有实现按目录名排序（`scanTasks` 内部决定）。
  若排序不稳定，翻页会重/漏。需要先确认扫描的排序是确定的。
- 这些都在规格阶段定死，不在实现时顺手决定。
