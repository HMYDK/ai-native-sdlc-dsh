## ⚠️ 五条必须知道的口径（不知道就会误读这个数字）

1. **等价变异算存活，但不是测试漏洞。** 改了一处而行为不变（对必然非 null 的值
   做 null 检查；`&&` 与 `||` 在"两者都成立"时等价……）会记为存活。
   **真实缺口比存活数小。** 本工具**没有做等价变异过滤**——这是最大的假信号源。
   实例：`scan.ts:601` 的 `a.stale && b.stale` → `||`，实测（直接跑两种实现对比）
   **排序结果完全相同**，是等价变异，不该为它写测试。
2. **"被抓住"没有区分原因。** 类型错误导致的编译失败也算"被抓住"——只统计退出码，
   没验证变红的原因是**断言**。
3. **源码行定位是文本匹配，有噪声。** tsc 会重排行，工具按"该行文本在 src 里找
   第一处相同内容"来定位。实测会指到 schema 定义或注释上（如 `src:261`、`src:132`）。
   `lib:` 行号是准的，`src:` 仅供参考。
4. **不能并发跑。** 实测：后台跑全量时再并发跑同一个包，两个循环同时改同一批文件，
   `sdlc-task` 出现过 79.1% / 99.1% / 只 1 个存活三个版本。
   **同理，跑这个工具时不要同时跑验证。**
5. **它是"改-还原"。** 在 `lib/` 上做文本替换，用 `tsc` 从源码还原，收尾 `git status`
   自检。但 `lib/` 不进 git，所以自检只能证明"没动 src"。

## 读这份报告该看什么

**不要只看总分。** 有用的信息在：

- **模块之间的差异**：`sdlc-task/state.ts`（状态机核心）只有 1 个存活，
  而 `sdlc-artifact/index.ts`、`sdlc-status/index.ts` 是几十个。
  **纯逻辑 + 直接单测 = 几乎无盲区**；反过来，接线层与文档层薄。
- **存活点的形态**，而不是数量。本轮人工看过一遍，多数落在
  ①只在工具 schema 保证下成立的防御性类型守卫（不可达）
  ②格式化代码里的 `const-*`（真假信号都有，要逐条看）
  ③极少数真分支（本轮找到 `scan.ts:601` 的"两个都停滞"分支从未被执行过）
