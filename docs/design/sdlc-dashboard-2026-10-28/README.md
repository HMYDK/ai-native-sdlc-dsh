# SDLC 看板三版设计探索

日期：2026-10-28。状态：等待用户选方向，尚未实施界面改动。

用户希望看板更有美感和足够的功能，能看清完整 SDLC，以及验证未通过后的修复、再验证循环。

## 现有问题与原因

目前的 `packages/sdlc/src/ui/client.js` 用当前状态在固定数组中的位置画单向阶段条；较早阶段全部按“已完成”处理，回退和反复进入同一阶段没有独立表达。概览主要展示最新裁决，历史藏在“迁移记录”页签中。

问题也在取数：`packages/sdlc/src/ui/index.ts` 返回阶段历史、最新裁决和 RSI 摘要计数，但没有逐轮验证、修复操作及其相互关联的视图数据。因此，仅添加回箭头或调整颜色不能让页面如实展示完整循环。

## 共同的功能设计

保留七个阶段：意图 → 规格 → 计划 → 实现 → 验证 → 评审 → 完成。修复是实现阶段内的活动，不新增一个与现有状态机不一致的顶层阶段。

所有方案都展示“验证未通过 → 修复实现 → 执行检查 → 再次独立验证”。通过后进入评审与完成；任务完成后的复盘可以产生新的改进任务，并回到正常开发流程。

选中某轮后，能查看当时发现的问题、对应修复、测试证据和复验结论。任务状态、当前活动、最新验证结论、执行记录是否完整分别表达。

概念中的点击包括：切换任务、选择阶段或验证轮次、展开发现、查看交付物与证据、查看工具调用记录、进入复盘。界面保持只读看板的既有边界。

Agent 执行轨迹表达可观测的目标摘要、工具调用、工具结果和下一步状态，不展示或补造隐藏推理。

## 选定后需要落实的数据规则

1. 阶段取自任务状态；验证轮次取自明确的验证运行 ID。同一次运行内部的重试单独展示为“尝试”，不算新的修复轮次。
2. 未通过不等于已返工。只有实际的回退或修复记录才能显示“正在修复”或增加返工次数，不能用 reject 次数直接推算。
3. 发现、修复、代码变更、测试与下一轮验证需要明确关联。现有记录不足时标记“关联待确认”或“未记录”，不能靠最近一条记录猜测。
4. 没有 finished 的运行不能一律当作仍在执行；需要区分已确认活动、取消、失败、未完成记录和状态未知。
5. 历史不足时展示缺口。任务完成、验证通过和执行记录完整是三件事，不能互相代替。
6. 浏览器应接收经过整理的任务摘要与按需详情；不会直接把原始 RSI 会话记录全部发给前端。
7. 宿主侧栏只是设计背景；最终实现限于插件主面板。图片中的额外宿主导航及生成的品牌图形不属于改动范围。

本轮交付为三张静态设计稿和上述取舍说明，尚未进行交互原型或运行时验证。选定方向后，再细化窄屏、深浅主题、空态、记录缺失、无裁决和人工确认状态。
