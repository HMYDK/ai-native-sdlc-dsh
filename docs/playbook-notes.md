## 原文的问题意识：写代码不再是瓶颈

原文的起点是一个已经发生的事实：组织用 AI 写代码的速度，超过了围绕代码的流程能吸收的速度。

传统 SDLC 不是无缘无故变重的。它诞生在“实现最贵”的年代：写代码要几周、几个月，所以需要 PRD、估点、评审会、签核，把有限的对齐机会用在长周期上。这些控制手段本身没有错，错的是它们默认的前提——每一步都由人执行，实现是成本中心。

当实现从数周缩到数小时，三个后果同时出现：

1. **瓶颈移到构建两侧。** 规划、评审/测试、部署仍按人的速度走；构建越快，等待越显眼。
2. **控制手段和现实脱节。** 逐行评审的前提是“人写的 diff”；当大部分 diff 由 agent 产出，逐行看既跟不上，也看不出真正的风险。
3. **治理成本上升。** 例外仍要走到周会、月会、委员会，等待时间成了新的成本中心。

原文用安全团队举例：编制按人的产出定，代码量成倍增长后，要么评审队列堆积，要么代码在评审不足时发布。受监管组织两个都不能接受。

所以原文的主张不是“减少控制”，而是**保留控制目标、更换执行方式**：策略从事后逐行看，移到事前写成约束、事中由机器执行、事后留下可核对的证据。判断仍由人负责，但人的注意力从“看每一步”移到“看门禁和制品”。

## 原文的骨架：制品链、六个阶段与人的位置

### 核心循环

原文把 AI 原生 SDLC 描述成一个闭环，而不是把 AI 塞进六个线性阶段。闭环的关节是**制品**：每个阶段以一份提交入库的制品收尾，下一阶段从读取它开始。原文用一句话概括这条链：每个阶段都以一份“下一阶段可以直接读取的制品”收尾。

Plan 交出 `intent.md`，Design 交出 `spec.md`，Build 交出 `plan.md`、diff 和测试，Test 交出可复现的检查结果，Deploy 交出带评审发现的 PR，Maintain 把事故和越界写成下一份 `intent.md`。

这条链有三个作用：交接不再靠会议和口头；每一步都有可核对的输入；提交历史本身成为审计线索——谁提出、agent 产出了什么、谁批准。早期是人手工触发下一步；成熟后被接受的制品自动触发下一道门禁，人的注意力集中在门禁处，而不是每个阶段都从零开始。

### 人的位置

原文没有把“人”写成瓶颈，也没有写成橡皮图章。它落在两点：需要判断力的决定由人负责，比如接受还是拒绝一份 spec、批准还是阻断一次发布；人的注意力跟着制品走，制品在哪里需要评审，人就在哪里出现。这两点决定了后面的治理设计：门禁要少而硬，证据要能被独立核对，审批要能追溯到具体的人。

### 每个 Play 的统一结构

六个阶段下面是若干 Play。每个 Play 都回答五个问题：有哪些变化；如何起步（前置条件、基础设施）；具体实施步骤；治理考量；如何衡量（先行指标、滞后指标）。

这个模板本身就是方法：它强迫写 Play 的人回答“怎么知道它有用”。Play 之间还有依赖图，采纳顺序不等于阶段顺序——可以从任何一个没有前置依赖的 Play 开始，不必从 Plan 开始。

### 一张对照表

| 阶段 | 传统做法 | 原文的 AI 原生做法 |
|---|---|---|
| Plan | 需求由委员会收集，研讨会加签核，人工写文档 | 提出者和模型把问题谈清楚，产出人和机器都能读的 `intent.md` |
| Design | 分析师写规格，设计师再解读 | 需求和设计合并成一次会话，约束以 Skill 形式在写的时候生效 |
| Build | 代码和测试手写，文档后补 | 先出计划再实现，组织知识写进 `CLAUDE.md` 和 Skill |
| Test | 阶段边界设 QA 门禁 | 每个会话先自检，评测贯穿实现过程 |
| Deploy | 人工逐行评审，治理靠评审周期 | 多层 agent 评审，人工只保留关键和受监管代码；治理在动作发生时执行 |
| Maintain | 人盯着生产找 bug | agent 监控，越界被诊断成新的 `intent.md` 回到闭环 |

## 六个阶段的关键做法

### Plan：把意图固定在提出者的语言里

转变不在“写得更快”，而在**意图不再经过层层转述**。提出者直接描述问题、受影响的人、约束和成功的样子，模型整理成 `intent.md`；产品负责人审阅、修正，再提交。

- 入口可以很多（一个想法、一张工单、一次告警），出口统一是一份版本化的意图。
- 模板可以固化成 Skill；非工程人员不必会用 git，模型可以代为提交。
- 治理证据就是提交记录：作者、时间、修订历史，以及接受或关闭的评审。
- 度量看两头：从第一次对话到提交的时间；被接受进入下一阶段的比例；spec 提交后 intent 又被改了几次。

这一步真正的价值是**给后面所有阶段一个可回溯的起点**。intent 不需要写得漂亮，但必须能让下一个阶段直接读。

### Design：需求与设计合并，策略在写的时候生效

传统流程里，需求和设计是两个团队、两个阶段，中间隔着一次信息损耗。原文把它们压进同一次会话：模型拿着 `intent.md` 产出规格，品牌、安全、合规、UX 的约束以 Skill 形式参与撰写，并在规格里**显式标出关注点**——尤其是几条规定互相冲突、无法同时满足的地方。

- 产品负责人评审规格，但不自己写；目标是产出一份工程团队能据以规划、且知道风险在哪的规格。
- 先手工跑，再固化成命令，最后由 intent 的接受事件自动触发。
- 规格、当时的提示词、参与约束的 Skill 版本，一起进版本控制。
- 关注点在被工程团队看到之前，先由产品负责人和对应策略负责人逐项处理。

度量看 intent 到 spec 的耗时，以及 spec 在计划开始之后又被改了多少次——后者是需求返工。**“标出关注点”是这一阶段最关键的设计**：它把“模型替你做了取舍”变成“模型告诉你它在哪儿做了取舍”，人才能在最便宜的时候介入。

### Build：先计划，再实现，把组织知识变成文件

原文把计划模式当作默认起点：模型可以读代码库，但不能改；工程师在代码写出来之前反复修计划，接受之后才进入实现。获批的计划作为 `plan.md` 入库，后面用最终的 diff 和它对照。

- `plan.md` 写到“没参与对话的工程师照着能做”：改哪些文件、什么顺序、用什么测试证明。
- 追问风险、被放弃的方案、可能被破坏的东西；实现偏离计划时，在同一次提交里更新计划。
- `CLAUDE.md` 放新成员第一天需要的信息：命令、约定、架构、模型最常犯的错。控制在一页以内，同一个错误犯两次就写进去。
- Skill 承载必须一致执行的组织知识；Hook 承载必须无例外成立的策略。原文把两者的关系说得很直接：Skill 降低违规概率，Hook 让违规几乎无法发生。
- 并行会话用 worktree 隔离，重复性工作交给子代理；但控制必须来自仓库里的配置，而不是会话里的口头约定。
- 每份制品要指定**事实来源**：仓库、遗留系统，或者至少互相链接。两个事实来源可以共存，但不能假装只有一个。

度量看首次实现即合入的比例、计划到合入的时长、返工轮次，以及合入的 diff 和 `plan.md` 的一致率。

`CLAUDE.md` 那条“同一个错误犯两次就写进去”是全文最可操作的组织学习规则：它把“知识管理”降级成“故障复盘的最小动作”，不需要专门的流程。

### Test：让会话自己先验，把独立复核留到最后

原文区分了两种验证，很多人会把它们混为一谈：**反馈闭环**贯穿整个任务，模型改一点、跑一次、自己修，便宜、连续、允许失败；**独立复核**在任务结束时，用干净的上下文重新看一遍，避免被实现时的假设污染。

前者的做法是给模型一条能自己跑的检查：一条命令、一个可量化的目标、一张能对比的截图。修 bug 时先写会失败的测试，确认它因为预期原因失败，提交，再在不改测试的前提下修——测试文件在修复期间要被锁住。UI 工作用截图迭代，两三轮是常态。最后把“验证”写进完成定义：报告完成之前必须跑检查并贴出输出。

后者是验证者子代理：独立上下文、受限工具、只报告不修改。原文特意区分两者：验证者子代理是最终检查的一种封装，不能替代过程自检。

持续评测是另一条线：从近期工作里取 20–50 个真实任务，每个写成“提示词 + 可接受的检查”，在配置变更时跑，事故转成常驻用例。评测套件是活的，模型变强后旧用例会失去区分度，要补新的。

度量看 CI 首次通过率、评审耗时、变更失败率，以及合并前发现和逃逸到生产的缺陷比例。这一段容易被读成“多写测试”。原文的重点其实是**把验证成本压到模型自己身上**：它能在人看到之前自己发现问题，人就不必充当第一道检查器。

### Deploy：评审双向，门禁保留在少数判断点

部署阶段不鼓励“让 AI 直接上线”，它做的是两件事：让评审更密，让审批更窄。

- **评审双向**：模型按组织政策评审别人的 PR，也处理自己 PR 上的意见；人把注意力放在意图和风险上。
- **`REVIEW.md` 定义评审本身**：分几轮（缺陷、安全、合规）、什么算 Important、什么算 Nit、Nit 最多报几条、哪些不报（生成代码、CI 已强制的）。
- **发现不直接批准也不直接阻断**：批准仍由分支保护下的人给出；希望用发现做门禁的团队，读取检查运行里的严重程度计数。
- **同一个错误第二次被指出时，把修正写进 `CLAUDE.md`**；评审还会标出某次变更让 `CLAUDE.md` 过时的情况。
- **Hook 作为审批门禁**：允许、询问、阻断；团队级放仓库，不可协商的放托管设置。阻断要能自我解释，告诉模型原因和获得批准的路径。
- **托管配置是组织持有的最后一道**：拒绝密钥、限制外联、沙箱不可用则拒绝启动、只允许托管 Hook、只允许批准的插件市场、最低版本。原文特意说，这是起点，不是照抄的建议。
- **CI/CD 先做只读的判断类步骤**（分诊失败、总结不稳定测试、起草变更日志），再做门禁之后的写入；部署能力通过 MCP 按环境暴露；开发环境放开，生产只准备发布，由发布经理授权；回滚要反复演练。

治理原则可以压成一句：agent 的行动范围止于生产门禁，门禁之后由人决定。度量看首次评审耗时、无需人碰分支就解决的评论比例、合并前发现的缺陷和逃逸到生产的缺陷，以及 DORA 指标。

这一阶段最容易被误读成“用 AI 替代评审”。原文的落点相反：它把人工审批**收窄到真正需要判断的少数门禁**，并且要求门禁由组织持有，不能由被约束的人自己关掉。

### Maintain：让生产事件变成下一份 intent

维护阶段把前面五个阶段接成一个环：触发器在没有人启动的情况下唤起模型，诊断结果以 `intent.md` 的形式回到 Plan。

- 选一个有稳定滚动基线的指标：CI 失败率、部署后 5xx、PR 周期。
- 检测脚本是**确定性的**：滚动均值、标准差、规则匹配，有版本控制、有单测，不涉及模型。
- 响应分级写进版本化配置：1σ 只记录，2σ 只读诊断，3σ 可以行动，但只能提 PR 或触发预先批准的 runbook。
- 运行是无状态的；诊断写成 `intent.md`，之后像任何工作一样流过分诊和门禁。
- 修复发布后，给评测套件补一条用例，防止同类问题复发。
- 周期扫描是同一模式的另一面：扫描是“某模型在某时点对某仓库的判断”，代码和模型都会过期，所以要按计划跑，发现先验证再报，修复走同样的门禁。
- 值班场景（事故频道）也是闭环的一部分：请求、诊断、授权、修复都留在同一个频道里，频道本身就是审计记录。

度量看越界到进入分诊队列的时间、发现变成已合并修复的比例、同类事故的复发率。维护阶段是原文里最像“终局”的一节，但它其实是在**生产下一个 intent**。闭环之所以能转，是因为最后一步和第一步用的是同一种制品。

## 落到本仓库：六个机制

### 为什么按机制拆，而不是按阶段拆

六个阶段听起来天然适合拆成六个模块，本仓库没有这么做。原因是 DSH 的扩展点和阶段并不正交：一条制品链会跨多个阶段，一个拦截点会被多个阶段用到。按阶段拆，会让同一条链分散在多个包里，同一个拦截点被多个插件重复注册。

所以本仓库的选择是：**执行按机制拆，分发按套件合一。** 一个 npm 包、一个 bundle，里面七个组件行各自独立运行；六个工作流组件放进「AI 原生 SDLC」模式，只读看板常驻宿主层。这不是原文的划分，是为了适配 Harness 扩展点做的工程决定。

### 机制对照表

| 原文的做法 | 本仓库的机制 | 边界 |
|---|---|---|
| 每个阶段以制品收尾，下一阶段读取它 | `state.yaml` 记录状态和制品索引；推进前检查制品是否存在 | 只查在不在、结构对不对，不判断内容质量 |
| spec 里的验收标准 | 稳定 ID 的验收标准，逐条对账 | 标准的质量仍要靠验证 |
| 验证者子代理 | `sdlc_verify` 启动独立会话，返回结构化裁决 | 不是操作系统级只读；模型判断不保证正确 |
| 评审发现 → 修复 → 复审 | `sdlc_task_issue` 登记、退回、提交、复验 | 作者不能自己关问题；阻断问题不能延期 |
| 修复期间锁住测试 | `sdlc_fix_start` / `sdlc_fix_end` 冻结测试资产 | 靠命名和命令模式识别；作者可以主动解冻 |
| 评测、事故转用例 | RSI：证据 → 提案 → 普通开发任务 → 新旧对照 | 不自动改代码；没有盲评隔离 |
| 门禁处的人 | 只读看板：阶段、路线、问题、轮次、缺口 | 只读，不提供审批动作 |

### 任务状态机与制品链

`.ai/tasks/<TASK-ID>/state.yaml` 是任务状态和制品索引的事实来源。七个状态是：

`INTENT → SPEC → PLANNED → IMPLEMENTING → VERIFYING → REVIEWING → DONE`

它不是六个阶段的直译：Plan 拆成了 INTENT 和 SPEC，Build 拆成了 PLANNED 和 IMPLEMENTING，Deploy 只走到 REVIEWING，DONE 表示流程内证据齐了，**不表示已合并或已上线**。

插件在这里的角色是“守护者”，不是“持有者”：每次从磁盘读状态，不缓存；人可以手改 `state.yaml`，下一次读就生效。每次推进都要写原因、过门槛，缺制品就拒绝；history 只追加，不修改。回退是合法的——计划错了就退回 PLANNED，但要记录原因。

代价也写得很清楚：状态机是**可检测、可审计**的，不是**不可绕过**的。手改文件能跳过门槛。这与仓库的边界一致：硬约束放在 Git/CI，客户端负责让违规显眼、让误操作变难。

对应原文，这一步把“制品被接受后触发下一阶段”落在状态迁移上。好处是能在动作发生前拒绝；代价是触发器不再天然等于提交，最终能不能合并仍由 Git 和 CI 决定。

### 独立验证与结构化裁决

`sdlc_verify` 启动一个不继承实现者上下文的验证会话。验证者有自己的一套工具：没有 `write`、`edit` 和任务推进工具，保留跑测试需要的 shell。裁决结构由插件侧请求，模型不能把它换成自由文本。

结果是三种之一：`approve`、`reject`、`needs_human`。每条验收标准都有独立结果，每个待复验问题都要单独回答；漏项、重复、未知编号、验证过程中内容发生变化、验证之后内容又变了，都不能作为通过依据。每轮裁决存进 `verifications/<run-id>.json`，连同它判断的那一版内容摘要。

这对应原文的验证者子代理和职责分离，但有一处刻意的收紧：原文说评审发现本身既不批准也不阻断，本仓库把验证裁决作为进入 REVIEWING 的条件。原因是这里的验证不是风格建议，而是按稳定 ID 逐条核对验收标准——它能被结构化，就应该被当作门禁。

边界也要说清楚：独立不等于只读，shell 仍然能写文件；独立也不等于正确，模型判断会有错；而且独立验证**测不了自己这次调用写出的产物**——它只能在调用期间观察，要验产物得另起一次。

### 问题逐项处理与复归

验证发现的问题自动进入任务，评审发现的问题通过 `sdlc_task_issue action=report` 登记。之后按固定编号处理：

1. `start`：说明原因和目标阶段。改需求退回 SPEC，改方案退回 PLANNED，改代码退回 IMPLEMENTING；只补证据可以留在当前阶段。
2. `submit`：填写实际改动和测试证据。这只代表作者提交，不代表问题解决。
3. 回到 VERIFYING，重新调用 `sdlc_verify`。验证者逐项返回结果，只有明确的 `resolved` 才关闭问题。
4. 非阻断建议可以 `defer` 并说明原因；阻断问题不能延期。

几个防止“假装修好”的细节：退回和问题动作在同一次保存里；直接调用 verify 也会检查未处理的问题，不能靠跳过推进来绕开；改了代码、规格、计划或验收标准后重新验证，必须有对应阶段的退回记录；单纯提交相同代码不会让上一轮裁决失效；完成后报告新问题会重新进入评审。

对应原文，这是“评审发现 → 修复 → 复审”循环的状态化版本。原文靠 PR 评论串和 `CLAUDE.md` 记住教训；本仓库先把教训固定在任务级问题上，再由 RSI 决定要不要上升成插件级改进。

### 测试冻结

修 bug 的顺序被固定下来：先写失败测试、确认复现，再调用 `sdlc_fix_start`；修复和复测完成后调用 `sdlc_fix_end`。冻结按仓库生效，拦截对已覆盖测试文件的写入，以及常见的 shell 改写方式。

对应原文，这是“修复期间用 Hook 阻止改测试”的同类机制，但强度不同：原文的 Hook 是确定性拦截，本仓库的冻结是**流程摩擦加留痕**——作者可以自己解冻，识别依赖文件名和命令模式，未覆盖的命名和等价写法会漏过去。

这是一个诚实的降级。客户端做不到硬约束，就不要假装做到了；冻结的作用是让“改松测试”这个动作变难、留下痕迹，而不是让它不可能发生。

### RSI 复盘

RSI 把记录单位从一次验证扩展到整个任务：作者做了什么、验证者查了什么、任务怎么变化、当时加载的是哪一版插件。它区分三个容易混淆的状态：

- `verification_complete`：拿到了结构化裁决；
- `evidence_complete`：已登记范围的证据通过了检查；
- `replay_ready`：运行有代码和会话起点，可以复跑。

三者不是一回事。任务完成不代表证据完整，证据完整也不代表可以盲评。

流程是：`sdlc_rsi_analyze` 读证据 → `sdlc_rsi_propose` 写问题、假设、尚未排除的解释、改动、验收和对照方法 → `sdlc_rsi_improve` 在插件源码仓库建一个**普通**的 INTENT 任务，不跳过开发流程 → 开发完成后做新旧两版对照 → `sdlc_rsi_feedback` 记录采用、拒绝或不确定 → 后续真实任务用 `followup_task_id` 跟踪实际效果。

对应原文，这是原文没有的一层：原文的评测对象是 agent 配置，本仓库把“流程本身”也变成可评测对象。对照要求两侧都有读数——旧版失败、新版满足判据，缺任何一侧都可能变成恒真断言。

边界同样明确：它不自动改代码、不自动安装；指导文字实验仍与参考答案共享文件系统，只能探索，不能据此推荐；确定性夹具证明的是机制，不是模型质量。

### 看板

侧栏的只读面板常驻，不提供任何工具。它把七个阶段、阶段交付物、每次推进和退回、逐项问题处理、历轮验证、记录缺口放到一起。

它多做的一件事是**按实际记录画路线**：需求问题退回 SPEC、方案问题退回 PLANNED、实现问题退回 IMPLEMENTING，显示的是来源、目标、后续路线和复验结果，而不是只给一个当前状态。记录缺失时显示缺口，不拿最新文件冒充旧证据；显式工作区没有该任务就返回 404，不借用别的工作区的同名任务。

对应原文，看板就是“人的注意力落在门禁和制品上”那个落点的实现。它还多了一层诚实：**没有证据的地方要显示出来**，而不是补一个看起来完整的故事。

## 刻意没有对齐的地方

### 止步于 DONE

插件不做发布授权、分支保护、密钥管理，也不碰生产监控。`DONE` 只表示流程内的证据齐了，不表示合并、不表示上线。原文的 Deploy 和 Maintain 大量依赖 Hook、托管配置、CI 和可观测性，这些都在 Harness 之外——本仓库不假装自己能覆盖。

### 客户端控制不是合规控制

仓库实测过：用 base64 编码执行一条被禁止的命令，就能绕过客户端的文本匹配。所以本仓库不实现“禁止 push main”这类策略，也不把插件描述成合规管控。它能做的是让流程状态、验证证据和问题处理变得可核对，让违规显眼。

### 不记录审批人

原文的治理强调“谁批准”。本仓库的 `state.yaml` 不记审批人，因为 DSH 的 approval 事件只记录结果，不记录是谁批的。于是“人的判断留在环内”在这里表现为：人可以随时读记录、改记录、拒绝推进，而不是“某个节点必须由某个角色签字”。

### 建议性控制的局限

Skill 是建议性的，没有强制力。仓库自己的结论是：只有 guard/deny 那一层才有约束力。所以两条 SDLC Skill 的定位是给验证者的判据清单，不是自动强制；它们能让验证更一致，但不能保证每次都被加载。

### 度量还没走完

原文每个 Play 都有先行和滞后指标，回答“这套东西到底有没有让流程变快、变好”。本仓库目前能自动产出的是任务级读数：裁决是否覆盖、问题是否闭环、证据是否完整、记录有没有缺口。这些是**流程健康**的代理指标，还不是周期、返工率、逃逸缺陷率那类结果指标。RSI 的后续反馈在往这个方向走，但还没有走到。

## 怎么读、怎么用

### 三种读法

- **十分钟版**：读“原文的问题意识”一节，再看六个阶段每节的首段和加粗句子，最后看机制对照表。
- **落地版**：先读原文的 Play 依赖图，选一个没有前置依赖的 Play 开始。本仓库的选择是先做验证——理由是结构化的 PASS/FAIL 是唯一能被严格自动验证的机制，计划的 markdown 很难自动判断好坏。
- **改造版**：把“落到本仓库”一节当成一个适配案例，重点看“哪些能搬进 Harness、哪些必须留在 Git/CI/RBAC”，而不是照搬工具名。

### 如果要动手

先回答三个问题，再决定做哪个机制：

1. 你的制品链断在哪一段？是意图没人写，还是规格没人核，还是验证没人信？
2. 哪些判断必须由人做？把这些做成门禁，其余交给机器。
3. 你用什么证明它有用？如果答不上来，先别做，先想度量。

原文结语的意思是：循环继续转，人的判断始终在它之上。本仓库做的事情，是让这个循环在 DSH 里留下可核对的痕迹。
