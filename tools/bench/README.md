# 基准：怎么验证「优化之后到底好了没有」

这套 SDLC 是照着真实任务逐步优化出来的。缺的一环从来不是"更多测试"，而是
**同一条判据在新旧两版代码上给出不同答案**。缺了它，为修复写的断言会向修复方案
归一化，变成恒真。

本项目实测发生过一次：STATUS-PAGE 第三轮，验证者发现作者新加的冒烟夹具只有
10 个任务，而 ≤50 时两种实现返回完全一样——**那条断言在被修好的代码和被 reject
的代码上都是绿的**。

所以每个基准用例都必须是**两侧对照**：

    基线版（有缺陷）  应当违反判据      ← 没有这一侧，用例是恒真断言
    当前版（已修复）  应当满足判据

## 现有用例

| 用例 | 脚本 | 基线 | 判据来源 |
|---|---|---|---|
| `sdlc-status` 默认页语义 | `tools/bench-status-page.mjs` | `60825a2` | intent「不改变默认行为」+ spec R1「向后兼容（逐字）」 |

判据**不是编写者编的**，是从当时的制品里搬来的。`60825a2` 的实现把默认路径也改成
按 task id 排序切窗，它自己违反了 R1。CI 与仓库自带测试都看不见，因为夹具是**同质**的
（id 序恰好等于紧迫序）。

    $ node tools/bench-status-page.mjs
    基线 60825a2  —  2/6 通过      ← 4 条判据被证伪
    当前 HEAD     —  6/6 通过
    ✅ 这是一组有效基准

退出码 0 = 两侧都符合预期；1 = 不符合（基线没被抓住，或当前版也违反）。

## 写新用例时必须守的三条

这三条都是踩出来的，不是规范抄的：

1. **夹具要让判据可证伪。** 夹具里必须同时有"该被看见的"和"不该被看见的"，
   规模要越过边界（这里是默认页上限 50）。踩过的坑：
   - 夹具 ≤50 时两种实现返回一样 → 断言恒真（历史真实发生）
   - 我写 `"同一 offset 跨时间给同一批"` 时，让**所有**任务同时跨过阈值，
     排序键相同、呈现序根本没变 → 又变成恒真。必须让**一部分**任务跨过去。
   - 我写 `"默认路径 == 传入顺序取前 50"` 时，断言的是基线自己的顺序 → 必然通过。
     改成断言"改动前实现会取的那一批"才有牙齿。

2. **state.yaml 必须写成真的 YAML 文本**，不能靠 `JSON.stringify` 拼。实测：
   用对象字段拼出来的内容 `status` 解析不出来，于是所有任务都被当成"健康"，
   紧迫任务不再排在前面——**夹具缺陷会让判据静默失效**。

3. **同时报守恒组。** 只报"该变的变了"是不够的：修复不能把"该拦的"一起放掉。
   `tools/bench-status-page.mjs` 的每一条都带观测值，便于看出哪些**没**变。

## 已知边界

- 用例数量还很少（1 条脚本 + 3 条已用探针实测过的历史 bug，见 AGENTS.md）。
  历史上可收集的**任务制品只有 3 个**（E2E-1 / STATUS-PAGE / WF-1，在 `f412a67` 被删、
  可从 git 历史取回）。所以用例的真实来源是**修过的 bug**，不是任务——
  每个 bug 天然自带 "坏的那版在父提交里、好的那版在修复提交里" 这一对。
- 需要**真实 Cordis 装配**的 bug（例如验证者整条通路）目前只能靠子代理临时探针测，
  还没固化进这个脚本。B3（`52212ad`）证明了可以用桩服务调用真实 `apply()` +
  真实 `ToolRuntime`/`createScope`/`restrict()` 测到，**不需要 Electron**——
  值得按同样手法固化。
